# v2.13.5 — Az üres dashboard javítása és a Codex-modell követése / Fixing the empty dashboard and following the Codex model

## Magyar

### 1. A dashboard nem maradhat „Várakozás az első pillanatképre” állapotban

- **Tünet:** friss indítás után a böngészőben a „Kapcsolat: Élő adatfolyam” látszott, de az „Adatok: Várakozás az első pillanatképre · Ismeretlen idő” felirat és az üres térkép sokáig nem változott, pedig a szerver már rég lefuttatta a sweepet.
- **Gyökérok:** a szerver minden SSE-üzenetnél (`broadcast`) és szívverésnél a `res.write()` hamis visszatérésére azonnal `destroy()`-t hívott. A Node viszont már akkor `false`-t ad, ha 16 KB-nál több van pufferelve; ez csak „várj a kiürülésre” jelzés, az adat ettől még megérkezik. Egy ~700 KB-os pillanatkép mindig ezt váltja ki, így a szerver a frissítés elküldése közben megszakította a kapcsolatot (`ERR_INCOMPLETE_CHUNKED_ENCODING`). A kliens újracsatlakozott („Élő adatfolyam”), de az adat sosem ért oda, a következő sweepig (15 perc) pedig ugyanez ismétlődött. Az indításkor kiszolgált üres oldal ráadásul csak egyszer kérte le az `/api/data`-t (503), és az SSE csatlakozása után nem próbálkozott újra.
- **Javítás:** a küldést az új [lib/sse.mjs](../../lib/sse.mjs) végzi: a kliens csak akkor kerül eldobásra, ha a puffere 32 MB fölé nő (valóban lemaradt kliens) vagy az írás hibázik. A szívverés ugyanezt használja. A kliens ([jarvis.html](../../dashboard/public/jarvis.html)) emellett újra lekéri a pillanatképet, ha az SSE-kapcsolat megnyílásakor vagy a 60 másodperces időzítőnél még nincs adata.
- **Reprodukció és igazolás:** izolált példányon (üres `runs`) a hiba pontosan így jelentkezett: 67 másodpercig „Várakozás…”, a 27. másodpercnél megszakadt adatfolyam. A javítással a sweep végén (t+27 s) megérkezik a pillanatkép, a felirat „Friss · Most” lesz, a kapcsolat nem szakad meg.

### 2. Codex: a `gpt-5.3-codex` modellt a ChatGPT-fiók már nem fogadja el

- **Tünet:** `Codex API 400: The 'gpt-5.3-codex' model is not supported when using Codex with a ChatGPT account` – az ötletgenerálás és a Discord-riasztás LLM-értékelése is szabályokra esett vissza.
- **Javítás:** `LLM_MODEL` nélkül az alapértelmezett modell a Codex CLI saját, fiókhoz tartozó listájának (`~/.codex/models_cache.json`) legjobb prioritású, listázott modellje; ha ez nem olvasható, `gpt-6.1-sol`. Így a következő modellcserénél sem kell kódot módosítani. Kézzel megadott `LLM_MODEL` változatlanul érvényes. A `.env.example` és a README frissítve.
- **Igazolás:** a végponton `gpt-6.1-sol` és `gpt-5.5` válaszolt, a `gpt-5.3-codex` 400-at adott.

**Ellenőrzés:** 7 új teszt ([test/sse.test.mjs](../../test/sse.test.mjs), [test/llm-codex-model.test.mjs](../../test/llm-codex-model.test.mjs)), köztük egy valódi HTTP-kapcsolaton átküldött 3 MB-os esemény. Célzott futás: 44 teszt, 0 hibás (az SSE, Codex, PWA, LLM-megbízhatósági és Grok tesztek). `npm run check` rendben. A teljes csomagot, a Node 22-es és a CRLF-es futást a „tartsd szűken” szabály szerint nem futtattam; a CI teszi.

**Átállás:** indítsd újra a szervert (`npm start`), hogy a javított SSE-kód és az új Codex-alapértelmezés életbe lépjen; a már megnyitott böngészőlapot frissítsd. Konfiguráció vagy adat nem változott. A PWA shell gyorsítótára változatlanul `crucix-shell-v2.13.0` (az online oldal hálózat-első).

**GitHub CI:** a v2.13.5 branch- és tag-futása piros lett egy oldal-teszt kiemelési listája miatt (`hasSnapshot is not defined`: [master-futás](https://github.com/mp3pintyo/Crucix/actions/runs/37606898758), [tag-futás](https://github.com/mp3pintyo/Crucix/actions/runs/37606898966)); a Docker-kép ezért nem készült el. A javítás a [v2.13.6](v2.13.6.md); ennek a kiadásnak a változtatásai abban élnek tovább.

## English

### 1. The dashboard must not stay on "Waiting for the first snapshot"

- **Symptom:** after a fresh start the browser showed "Connection: Live stream", but "Data: Waiting for the first snapshot · Unknown time" and an empty map stayed for a long time, although the server had finished its sweep long before.
- **Root cause:** for every SSE message (`broadcast`) and heartbeat the server called `destroy()` as soon as `res.write()` returned false. Node returns `false` once more than 16 KB is buffered; that only means "wait for drain", the data is still delivered. A ~700 KB snapshot always triggers it, so the server cut the connection while sending the update (`ERR_INCOMPLETE_CHUNKED_ENCODING`). The client reconnected ("Live stream") but never got the data, and the same happened again at the next sweep (15 minutes). On top of that, the empty page served at startup fetched `/api/data` only once (503) and did not retry after the SSE connection opened.
- **Fix:** sending now goes through the new [lib/sse.mjs](../../lib/sse.mjs): a client is dropped only when its buffer grows beyond 32 MB (a genuinely lagging client) or the write fails. The heartbeat uses the same helper. The client ([jarvis.html](../../dashboard/public/jarvis.html)) also re-requests the snapshot when it still has none as the SSE connection opens or on the 60-second timer.
- **Reproduction and proof:** on an isolated instance (empty `runs`) the bug appeared exactly so: 67 seconds of "Waiting…", with the stream cut at second 27. With the fix the snapshot arrives when the sweep ends (t+27 s), the label turns to "Fresh · Now" and the connection stays up.

### 2. Codex: the ChatGPT account no longer accepts `gpt-5.3-codex`

- **Symptom:** `Codex API 400: The 'gpt-5.3-codex' model is not supported when using Codex with a ChatGPT account` – idea generation and the Discord alert's LLM evaluation both fell back to rules.
- **Fix:** without `LLM_MODEL` the default is the best-priority listed model of the Codex CLI's own per-account list (`~/.codex/models_cache.json`); if that cannot be read, `gpt-6.1-sol`. The next model change then needs no code change. An explicit `LLM_MODEL` still wins. `.env.example` and the README are updated.
- **Proof:** the endpoint answered for `gpt-6.1-sol` and `gpt-5.5` and returned 400 for `gpt-5.3-codex`.

**Validation:** 7 new tests ([test/sse.test.mjs](../../test/sse.test.mjs), [test/llm-codex-model.test.mjs](../../test/llm-codex-model.test.mjs)), including a 3 MB event sent over a real HTTP connection. Targeted run: 44 tests, 0 failed (the SSE, Codex, PWA, LLM-reliability and Grok tests). `npm run check` passes. Following the "keep it lean" rule I did not run the full suite, the Node 22 run or the CRLF run locally; CI does.

**Upgrade:** restart the server (`npm start`) so the fixed SSE code and the new Codex default take effect, and reload any open browser tab. No configuration or data changed. The PWA shell cache stays at `crucix-shell-v2.13.0` (the online page is network-first).

**GitHub CI:** the v2.13.5 branch and tag runs went red because of a page test's lift list (`hasSnapshot is not defined`: [master run](https://github.com/mp3pintyo/Crucix/actions/runs/37606898758), [tag run](https://github.com/mp3pintyo/Crucix/actions/runs/37606898966)); no Docker image was built for it. The fix is [v2.13.6](v2.13.6.md); this release's changes live on there.
