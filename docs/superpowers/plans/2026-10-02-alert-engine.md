# Alert Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a rule-based alert engine (six rule kinds, alert lifecycle, persistence, Telegram/Discord/ntfy/webhook delivery) with an alert strip, tray, toasts and a rules editor in the dashboard.

**Architecture:** Pure server modules under `lib/alerts/` (levels, metrics registry, rules, evaluators, store, engine, notify, routes) run once per sweep inside `runSweepCycle()` behind their own try/catch and expose a summary on the snapshot plus a guarded `/api/alerts*` API and an SSE `alerts` message. The browser gets a pure `alerts-core.js`, a string-rendering `alerts.js` with a thin DOM controller, a rules editor module, and `alerts.css`.

**Tech Stack:** Node 22/24 ESM, Express 5, `node:test`, vanilla browser JS, optional Playwright QA (from `D:/AI/Jev/node_modules/playwright` via `PLAYWRIGHT_MODULE`).

**Spec:** `docs/superpowers/specs/2026-10-02-alert-engine-design.md`

## Global Constraints

- Node 22/24 ESM; no new runtime dependency (server or browser); no regex lookbehind in `dashboard/public/*.js` (a test enforces it).
- Levels: `critical|high|watch|info` (glyph ◆ ▲ ● ○ + colour, tokens `--sev-*` from `record-inspector.css`); threat 1–5 from `firing` alerts only (info 2, watch 3, high 4, critical 5; none = 1). `monitor` and `low` events are INFO; `moderate` WATCH; `elevated` and `high` HIGH.
- Rules: `id` `[a-z0-9-]{1,40}`, `name` ≤ 80, `forSweeps` 1–10, `cooldownMinutes` 0–1440, keywords ≤ 10 × ≤ 40 chars (plain substring, no regex), radius km 1–3000, ≤ 50 user rules, unknown fields rejected. Alerts: ≤ 1000 stored, 30 days, 20 log entries, evidence ≤ 8, ≤ 50 active per rule, `resolveAfterSweeps` 2, snooze 15 min – 7 days, snooze reason ≤ 120.
- Notifications: min severity default `high`, ≤ 5 individual per sweep then one digest, `silent` (bootstrap) alerts never notify, one notification per episode per channel (again on escalation), quiet hours let `critical` through. Channels are env-only; URLs http(s) without credentials; 10 s timeout; secrets never logged.
- API: guarded by the existing Basic auth; mutating routes need `Content-Type: application/json` (415), same origin (`Origin`/`Sec-Fetch-Site`, 403), body ≤ 8 KB, errors `{error, code, field}`.
- The alert engine must never break the sweep, the existing Telegram/Discord alerts or the delta engine; existing tests stay green; no private data in tests.
- Persistence under `runs/alerts/` through `lib/atomic-json.mjs`; corrupt or oversized files never stop the server.
- Every UI string in `locales/en.json`, `hu.json`, `fr.json` (`alerts.*`); parity test covers it. New static files go into `sw.js` `BASE` and `jarvis.html`; z-index: tray 950, toasts 1150.
- Commits end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; implementers never push, tag or publish. Version 2.10.0, `sw.js` cache `crucix-shell-v2.10.0` (last task only).

## Review Focus

- First run or upgrade with many existing critical events must create `silent` alerts and send no notification (Tasks 4, 5).
- One throwing rule, evaluator, notifier channel or store write must not stop other rules, the sweep or the broadcast (Tasks 4, 5, 6).
- A cross-site `POST` that carries cached Basic credentials, a non-JSON body, an oversize body and malformed JSON must all be rejected with JSON errors (Task 6).
- Hostile rule input (`__proto__`, huge arrays, regex-looking keywords, NaN/Infinity, wrong types, unknown fields) is rejected without effect (Tasks 2, 6).
- Time edges: snooze expiry across a restart, cooldown after resolve, clock going backwards, corrupt or empty store on restart (Task 4).
- Hostile text from feeds in alert titles/summaries must stay inert in the UI, Telegram/Discord/ntfy text and webhook JSON (Tasks 5, 7).
